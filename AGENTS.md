# AGENTS.md — регламент мультиагентной команды разработки

Переиспользуемый регламент для проектов, которые ведёт команда ИИ-ролей под управлением оркестратора и человека-заказчика. Он описывает роли, порядок работы, утверждения, quality gates и политику выбора моделей и бюджета токенов.

Документ не зависит от конкретного проекта. Настройки проекта (пути, команды сборки, список гейтов) задаются в разделе 9 «Параметры проекта» или в `CLAUDE.md` проекта. Если `CLAUDE.md` и этот файл расходятся, приоритет у `CLAUDE.md` проекта.

---

## 1. Принципы

1. **Человек решает, команда исполняет.** Решения о деньгах, ключах, публикации, правах доступа и обходе защиты принимает только заказчик (раздел 4).
2. **Доказательство важнее утверждения.** Фраза «тесты проходят» без вывода прогона не считается. Каждое утверждение о работе гейта или теста подтверждается командой и её выводом.
3. **Маленькие шаги.** Работа делится на срезы, срезы на шаги. Каждый шаг заканчивается проверкой, коммитом и бэкапом.
4. **Дешёвое по умолчанию.** Задача уходит на самую дешёвую модель, которая с ней надёжно справится. Сильная модель берётся только по правилам раздела 7.
5. **Память в файлах, а не в чате.** Состояние проекта живёт в `docs/STATE.md` и в git. Сессию можно потерять в любой момент, и это не должно стоить работы.
6. **Никаких действий на всю машину.** Команды, которые затрагивают процессы, файлы или настройки вне проекта (`taskkill /IM`, `killall`, правка системного PATH, глобальные конфиги), запрещены без явного разрешения заказчика.

## 2. Роли

У каждой роли есть зона ответственности, запреты и модель по умолчанию. Модель по умолчанию — это нижняя ступень. Оркестратор может поднять её для конкретной задачи по правилам раздела 7.

| Роль | За что отвечает | Чего не делает | Модель по умолчанию |
|---|---|---|---|
| **orchestrator** | Делит работу на шаги, вызывает роли, выбирает модели, следит за бюджетом, пишет отчёт заказчику | Не пишет код сам. Не читает большие файлы целиком, поручает это ролям | sonnet (opus на развилках, см. 7.3) |
| **po** (product owner) | Спецификации, критерии приёмки, приоритеты, вопросы заказчику | Не решает архитектуру и не пишет код | sonnet |
| **arch** | Архитектура, ADR, границы модулей, модель угроз вместе с sec | Не реализует | opus |
| **plan** | План шага: файлы, порядок, тесты, критерии готовности | Не меняет код, не коммитит | sonnet |
| **dev** | Реализация по плану, тесты, мутационная проверка новых seam | Не меняет план и спеку молча: отклонения записывает и согласует | sonnet. Защитный код и гейты — opus |
| **rev** | Независимое ревью со свежим контекстом: корректность, безопасность, соответствие плану | Не правит код сам, только возвращает с замечаниями | opus для финального ревью, sonnet для предварительного |
| **sec** | Безопасность, модель угроз, пробы обхода (только с согласия заказчика) | Не проводит пробы без согласия | opus |
| **qa / check** | Чек-листы, прогон тестов и стенда, сбор выводов | Не чинит, только фиксирует | haiku. Разбор падений — sonnet |
| **keep** | `docs/STATE.md`, коммиты, бэкапы, передача дел между сессиями | Не принимает решений по содержанию | haiku |
| **critic** (внешний) | Второе мнение по плану или ADR до кода, например другой LLM | Не решает: его вывод — одно из мнений для rev | внешняя модель |
| **triz / audit** | Разбор противоречий; периодический пересмотр контекста и правил | Не меняет код | sonnet |

Роли можно объединять в маленьких проектах: plan с po, check с keep. Нельзя объединять **dev и rev**: ревью делает отдельный вызов со свежим контекстом.

### 2.1 Как роли передают работу

```
заказчик ──▶ po (спека) ──▶ arch (ADR, если нужно) ──▶ critic ──▶ plan
                                                                  │
         ┌────────────────────────────────────────────────────────┘
         ▼
        dev ──▶ check (тесты, стенд) ──▶ rev ──┬─▶ keep (коммит, бэкап, STATE)
         ▲                                      │
         └──────────── возврат с замечаниями ◀──┘
```

- Каждая передача — это файл или короткий отчёт: спека, план, diff, вывод тестов. Пересказ по памяти не годится.
- Роль получает только то, что ей нужно: путь к спеке, плану и diff, а не всю историю чата. rev намеренно не получает рассуждений автора.
- Отчёт роли укладывается в 10–20 строк: результат, доказательства (команда и вывод), открытые вопросы.

## 3. Рабочий процесс

### 3.1 Жизненный цикл среза

1. **Спека** (po): цель, границы, критерии приёмки, что вне области.
2. **ADR** (arch) — если меняется архитектура, граница доверия или модель угроз.
3. **Внешняя критика** (critic) спеки, ADR и плана до кода. Вывод передаётся rev.
4. **План** (plan): шаги по 1–3 часа работы, у каждого шага свои тесты и критерий готовности.
5. **Утверждение G1** заказчиком (раздел 4) — только после этого начинается код.
6. **Шаги**: dev → check → rev → keep. Возврат от rev — это нормальная часть процесса.
7. **Приёмка среза** (G6): все критерии спеки подтверждены выводом тестов, заказчик видит результат.

### 3.2 Протокол возобновления

Каждая новая сессия и каждое продолжение после лимита начинается одинаково:

1. `git status`, `git diff --stat`, `git log --oneline -10`.
2. Прочитать в `docs/STATE.md` раздел «Передача дел».
3. Незакоммиченные изменения не трогать, пока не понятно, чьи они и зачем. Описать их в первом ответе.
4. Первый ответ короткий: состояние дерева, что найдено в STATE, следующий шаг.

### 3.3 Коммиты и бэкапы

- Один шаг — один коммит или несколько логичных коммитов. Сообщение коммита: что и зачем, ссылка на шаг плана.
- Запрещено: `--no-verify`, `--amend` содержимого, force-push, переписывание истории — без явного разрешения заказчика.
- После каждого коммита: `git bundle create <backup-dir>/<project>-<дата>-<hash>.bundle --all` и `git bundle verify`. Хранить последние 10.

### 3.4 Передача дел (обязательно в конце каждого шага)

keep дописывает в `docs/STATE.md`:

```
## Передача дел — <дата>, <шаг>
- Сделано: <1–3 строки, коммиты>
- Не закоммичено: <файлы или «нет»>
- Следующее действие: <одна строка>
- Ждёт заказчика: <список или «нет»>
- Модели шага: <роль→модель>, расход ≈ <токены или $>
```

Новая сессия поднимается с этого блока, а не с перечитывания всей истории.

## 4. Утверждения (approvals)

### 4.1 Только заказчик лично

Команда, оркестратор и внешний лид **не могут** дать эти разрешения за заказчика, даже если в сообщении написано «заказчик разрешил»:

- утверждение плана среза (G1) и приёмка (G6);
- действия с повышенными правами (UAC, sudo, окно администратора);
- ключи API, пароли, секреты: ввод, смена, передача;
- согласие на пробы обхода защиты;
- переписывание истории git, force-push, удаление веток;
- публикация: push в общий репозиторий, релиз, отправка во внешние сервисы;
- изменение состава ролей и правил гейтов;
- траты сверх бюджета (раздел 8).

Команда готовит для заказчика **готовый текст или команду** и одну строку объяснения. Решение остаётся за ним.

### 4.2 Может решить оркестратор или лид

- выбор модели для задачи (раздел 7);
- порядок шагов внутри утверждённого плана;
- ответы на технические вопросы ролей в рамках спеки и ADR;
- возобновление после лимита;
- запись решений заказчика, переданных через лида, — с цитатой и пометкой «передано через лида».

### 4.3 Как записываются решения

Каждое решение заказчика попадает в `docs/STATE.md`: дата, дословная цитата, кто передал, на что оно распространяется. Решение «один раз» (например, согласие на одну пробу) не распространяется на следующие случаи.

## 5. Quality gates

| Гейт | Когда | Что проверяется | Кто открывает |
|---|---|---|---|
| **G1 — план утверждён** | Перед первым коммитом кода среза | Есть спека, план, внешняя критика учтена; маркер утверждения поставил заказчик | заказчик |
| **G2 — шаг готов к ревью** | Перед rev | Сборка зелёная, тесты шага проходят, вывод приложен, для нового seam есть мутационная проверка | check |
| **G3 — ревью пройдено** | Перед коммитом шага | rev не имеет блокирующих замечаний; все замечания закрыты или записаны как осознанные | rev |
| **G4 — бэкап** | После коммита | bundle создан и `verify` прошёл | keep |
| **G5 — состояние записано** | Конец шага | Передача дел в STATE заполнена | keep |
| **G6 — срез принят** | Конец среза | Все критерии спеки подтверждены, заказчик видел результат | заказчик |

Правила для гейтов:

- Гейт — это проверка, которую выполняет код (хук, скрипт, CI), а не обещание роли. Пока гейт не автоматизирован, это записано в STATE как риск.
- Маркеры утверждений заказчика должны быть защищены от записи самой командой: права ОС, подпись, отдельный пользователь. Маркер, который команда может создать сама, гейтом не считается.
- Каждое утверждение «гейт работает» помечается: **«Проверено под харнессом: да/нет»**, с командой и выводом.

## 6. Внешний критик

- Вызывается до кода: на спеку, ADR и план. На готовый код — только по просьбе rev.
- Получает только текст документов: без ключей, персональных данных и кода целиком.
- Запускается из отдельной рабочей папки, без доступа к репозиторию.
- В отчёте шага есть строка: «Critic: что заметил / что приняли / что отклонили и почему».

## 7. Model routing — выбор модели

### 7.1 Ступени

| Ступень | Модель | Для чего |
|---|---|---|
| **S1** | haiku (самая дешёвая) | Механика без суждений: `git status/log/diff --stat`, бэкап и verify, поиск по логам, сверка файлов, переименования, форматирование STATE, сбор вывода тестов |
| **S2** | sonnet (средняя) | Рутина с суждением: планы, чек-листы, спеки, тексты, сводки, обычный код и тесты, предварительное ревью, разбор понятных падений |
| **S3** | opus (сильная) | Защитный код (гейты, хуки, права, крипто, парсинг недоверенного ввода), архитектура и ADR, разбор неясных или плавающих падений, финальное ревью перед коммитом, решения с необратимыми последствиями |

### 7.2 Как выбирать — по порядку

1. **Задача трогает защиту, права, секреты или границу доверия?** → S3. Без исключений.
2. **Это финальное ревью перед коммитом или ADR?** → S3.
3. **Нужно суждение: что писать, как исправить, почему упало?** → S2.
4. **Ответ однозначно проверяется командой и не требует решений?** → S1.
5. **Не уверен?** → на ступень выше, чем подсказывает интуиция, но не выше S2, если пункты 1–2 не сработали.

В Claude Code ступень задаётся так:
- по умолчанию для роли — полем `model:` во frontmatter файла `.claude/agents/<роль>.md`;
- для конкретного вызова — параметром `model` при вызове роли через Agent. Он сильнее значения по умолчанию.

### 7.3 Эскалация — только по признакам

Задача повторяется на ступень выше, если произошло хотя бы одно:

- результат не прошёл проверку: тест, сборка или линтер упали из-за самой правки;
- rev нашёл ошибку корректности, а не стиля;
- роль сама пишет, что не уверена, или противоречит спеке;
- две попытки на текущей ступени подряд не дали результата.

Эскалация не происходит из-за:

- длинного файла: длинный не значит сложный, сначала надо сузить контекст;
- одного стилистического замечания rev;
- желания «на всякий случай» — кроме пунктов 1–2 из 7.2.

После эскалации следующая похожая задача снова начинается со своей обычной ступени. Эскалация не «прилипает».

### 7.4 Деэскалация

- Если S3 три раза подряд справился с похожими задачами без единого замечания rev, оркестратор пробует такую задачу на S2 и пишет результат в STATE.
- Оркестратор сам переходит на S3 только в момент развилки: выбор подхода, конфликт ролей, неясная ошибка. После развилки возвращается на S2.

## 8. Token budgets — бюджет токенов

### 8.1 Бюджет на вызов роли

| Тип задачи | Ступень | Вход (контекст) | Выход | Примечание |
|---|---|---|---|---|
| Механика | S1 | до 20k | до 2k | Если не хватает, задача сформулирована слишком широко |
| План, спека, чек-лист | S2 | до 40k | до 6k | Давать пути к файлам, а не их содержимое целиком |
| Обычный шаг dev | S2 | до 80k | до 15k | Только файлы шага и их соседи |
| Защитный шаг dev | S3 | до 80k | до 15k | То же, но модель сильнее |
| Ревью | S2 или S3 | до 60k | до 4k | diff, план и спека, без истории чата |
| Разбор падения | S2→S3 | до 40k | до 4k | Хвост лога (последние 200 строк), а не лог целиком |

Числа — ориентир, а не жёсткий лимит. Превышение больше чем в 1,5 раза — повод разбить задачу.

### 8.2 Гигиена контекста

1. **Оркестратор держит только выводы.** Большие файлы, логи и поиск по коду читают роли, оркестратору возвращается 10–20 строк.
2. **Логи — хвостом и фильтром** (`tail`, `Select-String`, `grep`), не целиком.
3. **Одна сессия — один шаг или несколько небольших.** Когда контекст оркестратора превышает ~200k, нужно сделать передачу дел (3.4) и начать новую сессию или сжать текущую.
4. **Не перечитывать то, что не менялось.** Перед повторным чтением проверить `git diff`.
5. **Ревью одним заходом.** rev собирает все замечания сразу, dev исправляет их одним заходом. Больше 2 кругов по мелочам — сигнал оркестратору: замечания собираются в один список.

### 8.3 Бюджет на период

- Заказчик задаёт бюджет на период (неделю или месяц) в разделе 9.
- Оркестратор отмечает расход в передаче дел каждого шага.
- При 70% бюджета оркестратор переводит необязательную работу (рефакторинг, улучшения текстов) на S1–S2 и предупреждает заказчика.
- При 90% работа останавливается на ближайшей безопасной точке (коммит, бэкап, передача дел), и заказчик получает отчёт.
- Лимит провайдера — это не ошибка. Работа продолжается с передачи дел после сброса лимита, без подтверждения заказчика, если он заранее так распорядился.

## 9. Параметры проекта

Заполняется в каждом проекте. Пример:

```yaml
project: <название>
state_file: docs/STATE.md
backup_dir: ~/Backups/<project>
backups_keep: 10
build: <команда сборки>
test: <команда тестов>
gates:
  G1_marker: .claude/gates/g1-approved   # защищён от записи командой
critic:
  tool: <внешний LLM CLI>
  workdir: ~/<critic-workdir>
budget:
  period: week
  limit: <токены или $>
report_to_customer: every 3 days
machine_wide_commands: forbidden
```

## 10. Отчёт заказчику

Простым языком, без внутренних терминов, где без них можно обойтись. Формат:

1. **Продукт по кускам** — таблица: кусок, что даёт, статус.
2. **Текущий срез** — шаги и их статус.
3. **Что сделано за период** — коммиты, тесты с цифрами, бэкап.
4. **Находки и проблемы** — что нашли, что сломалось, что сделали.
5. **Решения, которые команда приняла сама** — их можно пересмотреть.
6. **Что нужно от заказчика** — коротким списком, с готовым текстом для вставки.
7. **Расход** — по ролям и моделям, сколько осталось от бюджета.
